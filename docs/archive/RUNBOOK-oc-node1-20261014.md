## Голос

**Распознавание — только локальное.** Аудио никуда не отправляется: облачные плагины
распознавания (deepgram, elevenlabs, azure-speech, openai-whisper-api) отключены,
ключей сторонних STT-сервисов в окружении сервиса нет.

Движок в конфиге ровно **один** — Parakeet. Запасной whisper вызывается изнутри
обёртки, если Parakeet упал или вернул пустоту:

| | Движок | Обёртка | Скорость |
|---|---|---|---|
| основной (в конфиге) | **Parakeet TDT 0.6B v3** (ONNX, CPU) | `/usr/local/bin/parakeet-cli` | ~7 с постоянных + 0.12x длительности |
| запасной (внутри обёртки) | whisper.cpp `ggml-medium-q5_0` | `/usr/local/bin/whisper-cli` | ~1.2x длительности |

Замер 2026-09-02 на записи 142 с: Parakeet 14.7 с против whisper 109.9 с в тёплом
состоянии; с холодным стартом полный вызов 12.8 с против 40.6 с. Точность на
синтетической речи вышла вничью (WER 26% против 24%), но метрика штрафует за
перевод чисел в цифры, который делают оба. **Итог по точности на реальной речи
собирается теневым режимом (см. ниже).**

Модель Parakeet лежит в `/opt/hf-cache` (2.4 ГБ), окружение — `/opt/parakeet`.
**Кэш вынесен из `/root/.cache` намеренно:** сервис работает от пользователя
`openclaw`, и со своим кэшем он качал модель заново при каждом вызове.
Обёртка выставляет `HF_HOME=/opt/hf-cache` и `HF_HUB_OFFLINE=1`.

**Теневое сравнение** (сейчас ВЫКЛЮЧЕНО, счётчик 0)**.** Пока счётчик `/srv/openclaw/stt-shadow.count` больше нуля,
после каждого голосового в фоне дополнительно отрабатывает whisper, и обе
расшифровки складываются рядом в `/var/log/openclaw/stt-shadow.log`.
На скорость ответа не влияет, аудио не сохраняется. Посмотреть:

```
/usr/local/sbin/stt-shadow-show.sh
echo 5 > /srv/openclaw/stt-shadow.count   # добавить ещё сравнений
```

**Откат на whisper** — поменять порядок двух элементов в `tools.media.models`.
Прежние конфиги: `openclaw.json.before-parakeet`, `.before-medium-switch`.

**Синтез** — провайдер `microsoft`, голос `ru-RU-SvetlanaNeural`, формат
`ogg-24khz-16bit-mono-opus`. Режим `auto: inbound`, `mode: final` — голосом отвечает
только на голосовые, текст идёт подписью. У Microsoft для русского **всего два
голоса**: `ru-RU-SvetlanaNeural` и `ru-RU-DmitryNeural`.

Синтез отправляет текст ответа наружу, в Microsoft. Полностью офлайновая
альтернатива — piper: `/usr/local/bin/piper-tts`, голос
`/opt/piper-voices/ru_RU-irina-medium.onnx`. Интерфейс обёртки:
**первый аргумент — выходной файл**, остальное текст (или текст на stdin);
расширение задаёт формат. Качество заметно ниже облачного.

Образцы для сравнения на слух: `/srv/shared/Media/TTS-образцы/`
(у вас на устройствах — `Agent/Media/TTS-образцы`).

### Выбор движка под задачу и диаризация спикеров (2026-10-08)

- **Просто расшифровка файла** (текст без меток): `sudo -u openclaw parakeet-cli
  -f <АБСОЛЮТНЫЙ путь> -of <база выхода>`. Только абсолютные пути — относительный
  путь делает ffmpeg падение незаметным (код 0 без результата, §3.9).
- **Расшифровка с разметкой по спикерам** («Голос 1/Голос 2/…» с таймкодами):
  `sudo -u openclaw env HF_HOME=/opt/hf-cache OMP_NUM_THREADS=8 \
  /usr/local/bin/diarize-run -f <АБСОЛЮТНЫЙ путь> -of <база выхода>`.
  Внутри: pyannote-диаризация (окружение /opt/miniforge/envs/pya) →
  parakeet-распознавание по сегментам. Долго: ~50 мин диаризации + ~10 мин ASR
  на часовую запись, CPU. Лог: `/var/log/openclaw/diarize-run.log`. Запускать
  фоном (nohup) и контролировать по логу, не ждать синхронно.
- **whisper-run НЕ использовать**: это запасной путь внутри parakeet-обёртки
  и ручной отладки (STT_PIPELINE=1), не боевой инструмент агента.
- Файл результата кладёт в Outbox (`-of /srv/shared/Outbox/<имя>-diarized`);
  имена голосов движок не присваивает — привязка к участникам вручную.
- Гейтованные модели pyannote и HF-токен: ***MASKED*** (640 root:openclaw),
  не логировать и не копировать в логи/репозитории.

Журналы движков: `/var/log/openclaw/parakeet-run.log`, `whisper-run.log`, `piper-tts.log`.

## Разобранные грабли

1. **uutils-coreutils.** Ubuntu 26.04 использует Rust-реализацию coreutils. Их `mkdir`
   в каталоге с default-ACL ставит режим `7775` — setuid и sticky. Sticky ломает удаление
   чужих файлов. Решение: отказались от default-ACL, работаем на setgid + `umask 0002`.

2. **Apache и initgroups.** `group_add` в compose добавляет группу процессу контейнера,
   но воркеры Apache вызывают `initgroups()` и берут группы из `/etc/group` **внутри
   образа**. Поэтому нужен кастомный образ `nextcloud-shared:34` с `usermod -aG shared www-data`.
   **При обновлении Nextcloud обязателен `docker compose build --pull`**, иначе группа потеряется.

3. **Права: проверять чтение, а не только запись.** Файл с режимом `0620` (группе запись
   без чтения) ломал всю синхронизацию Nextcloud. Нормализатор прав теперь проверяет оба бита.

4. **`restart: unless-stopped`.** Контейнер, остановленный **явно**, после перезагрузки
   намеренно не стартует. После ручного `docker compose stop` нужно поднимать руками.

5. **OpenClaw перезапускает себя сам** через `SIGUSR1` и выходит с кодом 0. В systemd-юните
   обязателен `Restart=always` — `on-failure` чистый выход за сбой не считает.

6. **Whisper и Ogg Opus.** whisper.cpp заявляет поддержку «ogg», но это Vorbis, не Opus.
   Telegram присылает Ogg Opus — нужна перекодировка.

7. **Плейсхолдеры CLI-моделей.** В `tools.media.models` обязательны поля `args` и `type: "cli"`,
   иначе команда запускается без аргументов. `{{OutputBase}}` уже содержит **полный путь** —
   склеивать с `{{OutputDir}}` нельзя.

8. **Агент может завести себе навык-костыль.** Пока штатная расшифровка была сломана,
   агент сам написал `Workspace/skills/local-audio-transcription/SKILL.md` и после починки
   продолжал вызывать whisper вручную — каждое голосовое расшифровывалось дважды
   (второй раз на полной 1.5 ГБ модели, ~3 минуты впустую). Навык архивирован в
   `/srv/openclaw/backups/`, правило закреплено в `AGENTS.md`, раздел «Голосовые сообщения».
   **Вывод: после починки любого тракта проверять `Workspace/skills/` на обходные пути,
   написанные во время поломки.**

9. **`tools.media.models` — это НЕ список «по очереди до первого успеха».**
   OpenClaw запускает **все** перечисленные модели и ждёт их все. Две модели в списке
   2026-09-02 привели к тому, что после успешной расшифровки Parakeet (24 с) параллельно
   стартовал whisper на те же 123 с звука, ответ бота завис на минуты и в итоге был
   потерян. **Правило: в списке всегда ровно одна модель, запасной путь — внутри обёртки.**

10. **`ProtectSystem=full` в юните гейтвея делает `/etc` только для чтения** для сервиса
   и всех его потомков. Писать состояние из обёрток можно только в `ReadWritePaths`
   юнита: `/srv/openclaw`, `/srv/shared`, `/tmp` (плюс `/var/log/openclaw`).
   Счётчик теневого сравнения живёт в `/srv/openclaw/stt-shadow.count` именно поэтому.

11. **Фоновые задачи из обёрток запускать только через `setsid`** и с отвязанными
   потоками. Иначе долгий фон держит родителя и задерживает ответ бота.

12. **Агент повторно расшифровывал уже расшифрованное — трижды на сообщение.**
   Конвейер OpenClaw сам вызывает движок **дважды** (предобработка входящего плюс
   подготовка вложения для агента), и сверх того агент запускал whisper вручную
   на полной 1.5 ГБ модели. Итог 2026-09-02: три расшифровки одного файла,
   load average 11, ответ висел минутами. Удаления навыка и правила в `AGENTS.md`
   **не хватило** — привычка воспроизводилась из истории сессии.
   **Решение: предохранитель в `/usr/local/bin/whisper-cli`** — без переменной
   `STT_PIPELINE=1` он отказывается работать и объясняет почему. Признак выставляют
   только `parakeet-cli` (запасной путь) и `stt-shadow-run.sh`.
   Для ручной отладки: `STT_PIPELINE=1 whisper-cli …`.

13. **CLI-движок распознавания должен печатать текст в STDOUT.** OpenClaw берёт
   расшифровку из стандартного вывода процесса, а не из файла, указанного в `-of`.
   whisper.cpp печатает текст попутно, поэтому с ним всё работало; самописная
   обёртка писала только файл — распознавание завершалось успешно, но вложение
   приходило агенту как `[Audio attachment could not be analyzed]`, и агент
   справедливо сообщал, что расшифровки нет. **Проверять обёртку так:**
   `OUT=$(обёртка … 2>/dev/null); echo ${#OUT}` — ноль означает поломку.

14. **Модели новее гейтятся по версии клиента.** OpenClaw 2026.8.2 по токену
   подписки представляется как **Claude Code 2.1.75**. Попытка переключиться на
   Fable 5.1 даёт `HTTP 400: "Claude Code 2.1.75 does not support this model;
   version 2.1.251 or newer is required"`, а `claude-fable-5` уходит в провайдер
   `claude-cli`, которому нужен установленный бинарь `claude` (его нет).
   Итог: бот отвечает «Something went wrong» на КАЖДОЕ сообщение, пока стоит
   переопределение. **Проверено рабочими:** `claude-sonnet-5`, `claude-haiku-4-5`,
   `claude-opus-4-7`.

   Переопределение модели живёт **в сессии**, а не в конфиге:
   `session_nodes.entry_json` -> ключи `modelOverride` / `providerOverride`.
   `oc models status` при этом показывает конфигурационное значение и вводит в
   заблуждение. Снимается остановкой гейтвея и удалением этих ключей.

15. **Обновление OpenClaw.** Ставится глобально через npm:
   `systemctl stop openclaw-gateway && npm install -g openclaw@<версия> && systemctl start openclaw-gateway`.
   Пакет ~900 МБ, установка около 30 секунд. Обновление 2026.8.1 -> 2026.8.2 (2026-09-02)
   прошло без правок конфига: `tools.media.models`, `tts`, `tools.profile`, обёртки
   и юнит systemd сохранились. Резервная копия перед обновлением:
   `/srv/openclaw/backups/upgrade-20260902-2242/`.

   **Версия Claude Code зашита в пакет** (`CLAUDE_CODE_VERSION=2.1.75`) и в 2026.8.2
   не изменилась — значит Fable 5.1, требующая 2.1.251, недоступна и после обновления.
   Ждать более новую версию OpenClaw.

16. **Правки конфига — только `openclaw config set` / `config patch`.** Они пишут
   через валидацию схемы. Ручное редактирование `openclaw.json` питоном опасно:
   неизвестный ключ (`plugins.entries.memory-core.dreaming`) даёт
   `status=78/CONFIG`, гейтвей не стартует. Настройки плагина живут под
   `.config`, а не рядом с `.hooks`:
   `oc config set plugins.entries.memory-core.config.dreaming.enabled false`.
   Проверка: `oc config validate`.

17. **Предохранитель от циклических перезапусков.** После нескольких неудачных
   стартов подряд гейтвей поднимается, но **каналы не запускаются**:
   `restart-loop breaker tripped: N unclean boot(s)`. Бот при этом молчит,
   хотя служба `active`. Лечение:
   `oc gateway call channels.start --params '{"channel":"telegram"}'`,
   плюс `systemctl reset-failed openclaw-gateway` перед следующим стартом.

18. **Плагинные автоматизации возвращаются после перезапуска.** `oc cron disable`
   действует только до рестарта гейтвея — плагин объявляет задачу заново.
   Выключать надо конфигом (см. п.16), тогда `oc memory status` показывает
   `Dreaming: off`.

19. **Проверка доступности модели без переключения конфига:**
   `oc agent --model anthropic/<модель> --session-key agent:main:probe -m 'тест'`.
   Прогон идёт в отдельной сессии, основную не трогает. Замер 2026-09-03:
   `opus-5`, `opus-4-8`, `sonnet-5` — HTTP 200; `fable-5-1` — HTTP 400
   (барьер версии клиента, см. п.14). Смена модели по умолчанию:

`ksu` настроен под чужого пользователя, поэтому отличается от остальных:

`doctor` предупреждает, если агент привязан к каналу, но не имеет инструмента

thread-reply могут не работать (обычный текстовый ответ работает всегда).

**Профиль `coding` инструмент `message` вырезает.** Поэтому предупреждение
касается `main` и `service`, а не агента Ксении.

У `ksu` (профиль `messaging`) добавлено точечно, без смены профиля:

```

```

Проверено 2026-09-04: агент подтверждает наличие `message` и отсутствие шелла.
Его полный набор: ***MASKED***
session_status, sessions_*, subagents.

### Что может и чего не может агент постороннего (проверено 2026-09-04)

Набор инструментов `ksu` (профиль `messaging` + `alsoAllow: ["message"]`):
`ask_user, conversations_*, intent, message, secrets, session_status,
sessions_*, subagents`.

**Чего у неё нет:** шелла, файловых инструментов, браузера, `web_search`,
`web_fetch`. То есть **выхода в интернет нет вообще** — только модель и переписка.

Проверено фактами:
- шелл — «нет доступа к выполнению команд в шелле сервера»;
- `sessions_send` в чужую сессию — **жёстко запрещён движком**:

- `secrets` — **только метаданные**, значение не возвращается никогда.

**Замеченная утечка метаданных: ***MASKED***
Агент Ксении видит имя `BASIP_PANEL_PASSWORD`, дату и разрешённые хосты
(IP панелей в лаборатории). Значение недоступно, но сам факт и адреса — видны.

**Не проверено технически:** отправка через `message` в произвольный
Telegram-чат. Агент отказался выполнять такую просьбу по собственному
суждению, распознав её как приём социальной инженерии. Дополнительная
защита на стороне Telegram: бот не может писать первым тому, кто ему
не писал.

**Инструмент `message` добавлен всем трём агентам** (`main`, `service` —
вместе с `browser`, чтобы не потерять его при переопределении списка).

### Длинные записи: parakeet режет аудио на куски

**Parakeet падает на длинных записях.** Он обрабатывает файл целиком, и на
записи 443 с рухнул в onnxruntime:

```
onnxruntime FAIL: Add node '/layers.0/self_attn/Add_2'
parakeet код=1 → запасной whisper (считал минутами)
```

`/usr/local/bin/parakeet-cli` теперь режет вход на куски по 150 с (ffmpeg
`-f segment`) и распознаёт их подряд **в одном процессе** — модель грузится
один раз, иначе накладные расходы съедают выигрыш. Результат склеивается
через пробел.

```
443,6 с → 3 куска → 6194 символа, код=0, 54,8 с
```

Пороги меняются переменными окружения, скрипт трогать не нужно:
`PARAKEET_CHUNK_SEC` (по умолчанию 150) и `PARAKEET_SPLIT_ABOVE_SEC` (180).
Прежняя версия — `/usr/local/bin/parakeet-cli.before-chunking`.

Границы кусков фиксированные: разбиение по паузам заметно дороже, а слово
на стыке теряется редко.

**Канал со своей стороны** на аудио крупнее 300 КБ сразу отправляет
подтверждение приёма — иначе минутная пауза выглядит как молчание и запись
присылают повторно.

### Грабля: фоновая работа из обработчика запроса отклоняется

Ответить вебхуку сразу, а разбирать в фоне — не выходит напрямую: запуск
агента падает с `GatewayDrainingError: Gateway is draining`.

Причина в `gateway-work-admission`: ядро помечает HTTP-запрос как «корневую
работу» в `AsyncLocalStorage` и освобождает её, когда обработчик завершился.
Фоновая задача остаётся в том же контексте и видит его освобождённым:

```js
isGatewaySubordinateWorkAdmissionClosed() {
  const current = currentRootWork.getStore();
  if (current) return current.released;   // ← отказ
```

Решение (сделано в 0.4.0): обработчик кладёт событие в очередь и сразу
отвечает 200, а разбирает очередь цикл, запущенный в `gateway.startAccount`.
Контекст аккаунта живёт всё время работы канала, оттуда запуск проходит —
ровно поэтому у опроса эта проблема не возникала.

Ответ вебхуку теперь уходит за ~0,04 с вместо всего времени работы агента.

### Что умеет

- Приём текста через `GET /updates` (long polling), ответ через `POST /messages`.
- Политики `dmPolicy` (`pairing`/`allowlist`/`open`/`disabled`) и `allowFrom` —
  та же модель, что у Telegram.
- Несколько аккаунтов: `channels.max.accounts.<id>`, значения аккаунта
  перекрывают корневые.
- Токен из файла (`tokenFile`), как у остальных ботов.
- 20 тестов (`npx vitest run`), typecheck против SDK установленного гейтвея.

### Чего нет (следующие фазы)

- Вебхук. MAX рекомендует его для прода, long polling — «для разработки»
  и ограничен по скорости. Caddy для этого уже готов.
- Вложения, голос, медиа. Сейчас сообщение без текста просто пропускается.
- Курсор `marker` живёт в памяти процесса: после перезапуска канал стартует
  с текущего момента. Долговечная очередь `createChannelIngressMonitor` — потом.
- `pairing.notify` шлёт код через аккаунт по умолчанию; сопряжение проще
  делать вручную через `openclaw pairing approve`.

### Грабля: осиротевшая запись реестра установок

`rm -rf ~/.openclaw/extensions/max` **не** снимает плагин. Запись остаётся в
SQLite, в `config_machine_state`, ключ `plugins.installedIndex` → любая
следующая установка падает:

```
Plugin package "max" has no authoritative runtime child list.
```

и **откатывается**, так что каталог не появляется. Сообщение советует
`plugins registry --refresh` — не помогает: обновление в отсутствие файлов
только закрепляет пустой индекс.

Лечение — снимать штатно: `oc plugins uninstall max --force`.
Если уже сломано, вычистить запись напрямую:

```python
import json, sqlite3, time
con = sqlite3.connect('/srv/openclaw/.openclaw/state/openclaw.sqlite')
row = con.execute("SELECT value_json FROM config_machine_state "
                  "WHERE state_key='plugins.installedIndex'").fetchone()
d = json.loads(row[0]); idx = d['index']
idx['installRecords'].pop('max', None)
idx['plugins'] = [p for p in idx['plugins'] if p.get('pluginId') != 'max']
con.execute("UPDATE config_machine_state SET value_json=?, updated_at_ms=? "
            "WHERE state_key='plugins.installedIndex'",
            (json.dumps(d, ensure_ascii=False), int(time.time()*1000)))
con.commit()
```

Бэкап базы перед правкой обязателен.

### Прочие грабли этого этапа

- Установщик **копирует каталог целиком**, поле `files` из package.json не
  учитывает. Из каталога разработки уехало 366 МБ (node_modules + .git).
  Ставим чистую выкладку — 80 КБ.
- Установка из **tgz-архива** не работает: тот же «no authoritative runtime
  child list». Только каталог.
- `oc plugins uninstall` без `--force` **висит** в неинтерактивной сессии,
  ожидая подтверждения. Всем вызовам `oc` в скриптах давать `< /dev/null`.
- Каналу нужен `--accept-capabilities` при установке.
- `createChannelPluginBase` не принимает `gateway` — поллер подключается
  к уже собранному объекту канала: `maxChannelPlugin.gateway = {...}`.
- `declaration: true` в tsconfig ломает сборку (`TS2742`, непортируемый
  выведенный тип); плагину декларации не нужны.

### Идентификаторы: номер аккаунта ≠ user_id в Bot API

Номер аккаунта, под которым бот создавался, зашит в его имя
(`se13558552_1_bot` → `13558552`). Bot API оперирует **другим** идентификатором:
в событиях приходит `3498912`. В `allowFrom` нужен именно он.

Узнать просто: написать боту и посмотреть журнал — отказ печатает id
отправителя. `/chats` для этого не годится: MAX отдаёт по нему zip
с `logcat.txt` вместо JSON.

### Грабли публикации

- **CRLF.** Правки файлов питоном с Windows переводят строки в CRLF, и
  shell-скрипты ломаются: `set: pipefail: invalid option name`. Лечение —
  `sed -i 's/
$//'` или писать с `newline='
'`.
- В тесты легко утекают **реальные идентификаторы** — при написании тестов
  на живых данных заменять их вымышленными сразу, а не перед публикацией.
- Собранный `.tgz` попал в индекс git; добавлен в `.gitignore`.

### Грабли запуска (04.09.2026)

- **Ответ шлём в `recipient.chat_id`, не в `recipient.user_id`.** В диалоге
  `recipient.user_id` — это сам бот (кому адресовано входящее). Отправка по нему
  даёт `MaxApiError: Invalid chatId: 0`, агент отрабатывает, а ответ теряется.
  `chat_id` универсален и для диалога, и для группы.
- **`install-local.sh` по умолчанию зовёт `openclaw`, а не `oc`.** Под root это
  пустой `/root/.openclaw`, и установка проходит мимо цели с ошибкой
  «Plugin artifact has no valid plugin manifest». На этом сервере запускать как
  `OC_BIN=oc STAGE_DIR=/srv/openclaw/dev/max-pkg bash scripts/install-local.sh`.
- **`plugins uninstall` сносит и секцию `channels.<id>` из конфига** — токен,
  политики, allowFrom. Переустанавливать только поверх:
  `plugins install <путь> --force --accept-capabilities`, без uninstall.
  Так и сделано в `scripts/install-local.sh`.
- **Маршрут обязателен.** При нескольких агентах ядро отказывается угадывать:
  `AgentSelectionRequiredError: max account default routing has no explicit owner`.
  Привязки живут в верхнеуровневом массиве `bindings`, а не в `agents.entries.*`.
- Правка `channels.max.*` перезапускает **только этот канал** (объявлено в
  `reload.configPrefixes`), телеграм-боты не трогаются. Правка `bindings`
  требует полного перезапуска гейтвея.

### Nextcloud разрушает git: причина повреждения установлена (2026-09-16)

Репозиторий `bas-ip-monitor` однажды уже восстанавливали (коммит `9fc0e10`), причину тогда
не разбирали. Теперь установлена: **каталог синхронизируется через Nextcloud, и в `.git`
писали двое** — агент на сервере и десктопный клиент на машине владельца.

Улики внутри `.git`: файлы пользователя `www-data` (это Nextcloud), включая объекты от 10.09
и `sourcetreeconfig.json` от 15.09 — его создаёт SourceTree.

```bash
# проверка на чужого писателя в служебном каталоге
find /srv/shared/Workspace/bas-ip-monitor/.git ! -user openclaw -printf '%u %T+ %p
'
```

**Потерь нет.** Битые объекты недостижимы — мусор от прошлого восстановления. Контрольный клон
с GitHub: 53 коммита, ноль ошибок, `HEAD` совпадает. Живая история цела.
`git gc` при этом падает с `bad tree object` и мусор не вычищает — косметика, работе не мешает.

**Сделано:** `.git` и `.archive` исключены из сканера Nextcloud.

```bash
docker exec -u www-data nc-app php occ config:system:set excluded_directories 0 --value=".git"
docker exec -u www-data nc-app php occ config:system:set excluded_directories 1 --value=".archive"
```

**Не закрыто (`OPS-3`):** в индексе Nextcloud осталось около тысячи записей о `.git` —
исключение действует только на будущие сканирования. Решение, держать ли рабочие репозитории
внутри синхронизируемого каталога, за владельцем. Удаление записей напрямую из БД Nextcloud
требует его согласия.

**Вывод:** git-репозиторий и файловая синхронизация несовместимы. Если каталог синхронизируется,
`.git` исключается **до** первого клонирования, а не после первой поломки.

`docker/docker-compose.yml` строкой `name: basip-monitor`. Поэтому тома переживают смену
каталога — compose находит их по имени проекта, а не по пути.

```bash
cd /srv/shared/Workspace/bas-ip-monitor
docker compose -f docker/docker-compose.yml --env-file .env down
mv /srv/shared/Workspace/bas-ip-monitor /srv/projects/bas-ip-monitor   # одна ФС → атомарно
cd /srv/projects/bas-ip-monitor
docker compose -f docker/docker-compose.yml --env-file .env config -q   # разбор ДО запуска
docker compose -f docker/docker-compose.yml --env-file .env up -d
curl -s -o /dev/null -w '%{http_code}\n' https://paylama.online/healthz   # ждём 200
```

Простой около минуты. `up -d` **без** `--build` — образ уже собран, пересборка тут не нужна
(`make up` делает `--build`, для переноса это лишнее).

Откат, если compose не разобрался: `mv` обратно и поднять на старом месте. Проверка разбора
идёт до `up`, поэтому откатываться приходится только при испорченном compose, а не при
неудачном старте.

### Побочный выигрыш, ради которого стоило это делать

В синхронизируемом каталоге лежали `.env` с паролем базы и `secrets/master.key` боевого стека —
и уезжали на компьютер владельца вместе с остальными файлами. После переноса не уезжают.
При заведении новых проектов проверять это первым делом.

### Хвосты в индексе Nextcloud

Перенос вычистил индекс сам: строк в `oc_filecache` стало 648 вместо 1607 — Nextcloud заметил
исчезнувшее поддерево и снял 959 строк. `occ files:scan` после этого показывает ноль изменений.

Остаток пришлось снимать точечно, потому что сканер **не заходит** в исключённые каталоги и,
значит, не помечает их записи удалёнными: 59 строк `Workspace/.git*` (storage 3) и 50 строк
`files_versions/Agent/Workspace/bas-ip-monitor/*` (storage 2) плюс 268 КБ файлов версий на диске.
Строки `media/inbound/*/.gitignore` — настоящие файлы агента, их не трогать.

```bash
# дамп ПЕРЕД любой правкой базы
docker exec -u postgres nc-db pg_dump -U nextcloud nextcloud | gzip \
  > /srv/openclaw/backups/nextcloud-db/nextcloud-$(date +%Y%m%d-%H%M%S).sql.gz

# файлы версий .git с диска
rm -rf /srv/nextcloud/html/data/admin/files_versions/Agent/Workspace/bas-ip-monitor

# индекс: удалять в транзакции, вместе со связанными таблицами
docker exec -i -u postgres nc-db psql -U nextcloud -d nextcloud <<'SQL'
BEGIN;
CREATE TEMP TABLE doomed AS
SELECT fileid FROM oc_filecache
WHERE (storage = 3 AND (path = 'Workspace/.git' OR path LIKE 'Workspace/.git/%'))
   OR (storage = 2 AND path LIKE 'files_versions/Agent/Workspace/bas-ip-monitor/%');
SELECT count(*) FROM doomed;
DELETE FROM oc_filecache_extended WHERE fileid IN (SELECT fileid FROM doomed);
DELETE FROM oc_files_metadata      WHERE file_id IN (SELECT fileid FROM doomed);
DELETE FROM oc_filecache           WHERE fileid IN (SELECT fileid FROM doomed);
COMMIT;
SQL
```

Соответствие хранилищ: `1` = данные Nextcloud, `2` = домашнее хранилище admin,
`3` = внешнее хранилище `/Agent` → `/mnt/shared` (оно же `/srv/shared` на хосте).
Проверять перед удалением: `select numeric_id, id from oc_storages;`.

**Грабля: `docker exec` без `-i` не подключает stdin.** Heredoc с SQL уходит в никуда,
psql запускается без запроса, команда завершается успешно и **ничего не делает**. Первый
заход по чистке именно так и прошёл — «выполнилось», а записи остались. Для heredoc всегда
`docker exec -i -u postgres nc-db psql …`.

**Сделано 2026-09-16.** Удалено 135 записей, в `oc_filecache` осталось 539 строк:
следов `.git`-деревьев ноль, следов `bas-ip-monitor` ноль, записей без существующего
родителя ноль. Контрольное `occ files:scan` — ноль новых, ноль удалённых, ноль ошибок.
Проверка целостности после любой правки индекса:

```sql
select count(*) from oc_filecache c where c.parent <> -1
  and not exists (select 1 from oc_filecache p where p.fileid = c.parent);
```

## Что агент видит за пределами своего каталога (2026-09-16)

Вопрос возник, когда проект переехал в `/srv/projects`, а рабочий каталог агента остался
в `/srv/shared/Workspace`.

**Права не мешают.** `tools.fs.workspaceOnly` по умолчанию **выключен** и относится к отправке
локальных файлов вложением, а не к чтению. Агент читает всё, что читает пользователь
`openclaw`. Проверено: `sudo -u openclaw head` по файлу в `/srv/projects` работает.

Обратное верно для записи: `tools.exec.applyPatch.workspaceOnly` по умолчанию **включён** —
`apply_patch` за пределами рабочего каталога не пишет. Править файлы проекта агент может
только через шелл. Это стоит помнить, поручая ему работу по проекту.

Ни то, ни другое в `openclaw.json` не задано — действуют умолчания. Проверять так:

```bash
sudo -u openclaw HOME=/srv/openclaw openclaw config get tools.fs
# «Config path is valid but unset» = действует умолчание рантайма
```

**Мешают ссылки, а не права.** Агент найдёт документ, только если на него есть ссылка
в том, что он читает в начале сессии: `AGENTS.md`, `MEMORY.md`, `docs/СОСТОЯНИЕ.md`,
`docs/ИНДЕКС.md`. Новый документ в репозитории проекта для агента не существует, пока
ссылки нет. Проверка:

```bash
grep -rn "<имя-документа>" /srv/shared/Workspace/ | head
```

Правило: кладя документ в проект — **тем же заходом** ставить ссылку в `ИНДЕКС.md`,
а если документ меняет приоритеты, то и в `СОСТОЯНИЕ.md`, потому что реестр долгов
агент читает раньше.

### Грабля: pip кладёт мимо пути (Debian double-local)

`pip install --prefix=/usr/local` на Debian и Ubuntu создаёт **лишний уровень** и кладёт
пакет в `/usr/local/local/lib/python3.14/dist-packages`, которого нет в `sys.path`.
Пакет установлен, импорт падает. Лечится переносом:

```bash
mv /usr/local/local/lib/python3.14/dist-packages/* /usr/local/lib/python3.14/dist-packages/
find /usr/local/local -type d -empty -delete
```

Проверять после любой такой установки: `python3 -c "import <модуль>"`, а не по выводу pip.

### Конвертация — только обёрткой `/usr/local/bin/soffice-convert`

```bash
soffice-convert pdf отчёт.docx            # печатает путь к готовому файлу
soffice-convert pdf таблица.xlsx /srv/out
soffice-convert csv таблица.xlsx
```

Обёртка закрывает две грабли, на которые наступили при настройке:

1. **`/usr/bin/soffice` делает `cd` в текущий каталог.** Запуск из недоступного каталога —
   например `sudo -u openclaw` из `/root` — даёт `cd: can't cd to /root`, конвертация
   не происходит, а диагностика теряется, если вывод заглушен. Обёртка уходит в свой
   временный каталог.
2. **Два одновременных запуска дерутся за профиль пользователя**, и один молча ничего
   не делает. Обёртка даёт каждому запуску отдельный `-env:UserInstallation`.

Проверено от имени `openclaw`: docx, xlsx и pptx конвертируются в PDF, кириллица остаётся
в текстовом слое (`pdftotext` её достаёт), два параллельных запуска дают оба файла,
обратная конвертация xlsx → csv работает.

## Захват трафика: tshark (2026-09-24)

Поставлен, чтобы различать «панель не отвечает» и «пакеты не доходят» — по журналам это
неотличимо, и на этом уже спотыкались при разборе смерти RTSP-службы.

```bash
echo "wireshark-common wireshark-common/install-setuid boolean true" | debconf-set-selections
DEBIAN_FRONTEND=noninteractive apt-get install -y tshark
usermod -aG wireshark openclaw
```

Первая строка обязательна: пакет спрашивает через debconf, разрешить ли захват
непривилегированным пользователям, и без заранее данного ответа установка встаёт.
Ответ «да» ставит `dumpcap` возможности `cap_net_admin,cap_net_raw=eip` и отдаёт его
группе `wireshark`.

### Группа без перезапуска службы

`usermod -aG` не меняет состав групп **уже запущенного** процесса OpenClaw — он определился
при старте службы. Перезапускать её ради этого не нужно и не следует: на перезапуске шлюза
на ходу мы уже теряли сообщения владельца. Вместо этого команда запускается в новой группе:

```bash
sudo -u openclaw HOME=/srv/openclaw sg wireshark -c "tshark -i any -c 100 -w /tmp/cap.pcapng"
```

Чтение снятых файлов группы не требует вовсе.

### Проверено сквозным опытом

Снят настоящий SIP-пакет через loopback и разобран от имени `openclaw`: `tshark` определил
протокол SIP, вытащил метод `REGISTER`, `r-uri` и `Call-ID`. Разборщики `sip`, `rtsp`, `rtp`,
`http`, `tcp` на месте.

**Грабля проверки, не самого tshark:** `tshark -G protocols` отдаёт имя фильтра в **третьем**
поле, а не в первом, и при запуске от root пишет в stderr предупреждение
«Running as user root». Из-за этого первая проверка объявила, что нет ни одного разборщика,
включая `tcp`. Если проверка утверждает, что в Wireshark нет TCP — неверна проверка.

### Правила

- Каждый захват ограничивать: `-c`, `timeout` или кольцевой буфер `-b duration:3600 -b files:24`.
  Иначе процесс переживёт задачу и забьёт диск.
- Файлы — в `/srv/openclaw/captures/` (создан, `openclaw:openclaw 750`).
- **Наружу не отдавать и в Nextcloud не класть:** панели опрашиваются по обычному HTTP,
  в захвате их пароли открытым текстом.
- Записано агентам: раздел в `AGENTS.md` обоих (грузится в стартовый контекст),
  рецепты в `/srv/shared/Workspace/docs/Захват-трафика.md`, строка в `ИНДЕКС.md`.
  Агенту `ksu` недоступно — у него нет шелла.

#### Когда резерв НЕ сработает (важно, 28.09.2026, вечер)

Цепочка подменяет модель **не всегда**. Перед выбором модели стоит гейт повтора:
если ход уже дал побочные эффекты — отправлено сообщение, запущена внешняя задача,
произведена запись в cron, — подмена **не пробуется вообще**. Система возвращает
`action: "proceed"` мимо всей ветки failover, и пользователь видит сырую ошибку
провайдера как есть. В логе при этом **нет строк `model-fallback/decision`**, а рядом
может стоять `incomplete turn detected ... replaySafe=no ... surfacing error to user`.

Это **защита**, а не дефект: повтор хода другой моделью продублировал бы уже
выполненное. Практический вывод: на резерв можно рассчитывать только для ходов
**без** побочных эффектов; в длинных агентных прогонах с инструментами он бессилен
по построению. Подробный разбор — §3.5, смягчение формулировки для пользователя — `OPS-6`.

Диагностика при жалобе «снова сырая ошибка» — **проверять обе причины**, они выглядят
одинаково:

```bash
# было ли решение цепочки вообще? если строк нет — это §3.5, а не мёртвый резерв
journalctl -u openclaw-gateway --no-pager --since "-2 hours" | grep -E 'model-fallback/decision'
# пометка неповторяемого хода
journalctl -u openclaw-gateway --no-pager --since "-2 hours" | grep -E 'incomplete turn detected|replaySafe=no'
```

3. **`baseUrl` обязан оканчиваться на `/v1`** для `openai-completions`. У существующих
