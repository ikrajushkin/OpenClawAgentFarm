# ADR-006 — Мультипроектность агентов

- **Статус:** принят 2026-10-21 (этап E5, OPF-9/T7); дополнен решениями E6/T8
  2026-10-21 (пилот — только `service`)
- **Контекст:** план «Фабрика агентов» §7 — агент работает с одной областью данных
  (workspace); нет независимых проектов со своими документами/памятью и переключения
  командами чата (OPF-9). В OpenClaw 2026.8.2 для этого есть готовые механизмы:
  workspace bootstrap-файлы (Project Context), навыки = slash-команды, `contextInjection`.
  План §7 оставил 4 открытых вопроса — здесь они закрыты.

## Решения

1. **Семантика переключения — per-агент (одно активное состояние на агента), не per-чат.**
   Агент ведёт один «текущий проект» на все чаты. Обоснование: пилот и так в одном
   контуре (`service`), состояние = файл в workspace, простота и предсказуемость.
   Per-чат изоляция (session-state) — отложена; не требуется для T7.
2. **Гидратация контекста при переключении** — карточка проекта `<dir>/PROJECT.md`
   (читается навыком `/проект` при каждом переключении; при отсутствии создаётся).
   Реестр проектов и правила доступны **в каждом ходе**: они в блоке «Проекты»
   `AGENTS.md` — одном из фиксированных workspace bootstrap-файлов (Project Context).
3. **Хранение «текущего проекта» между сессиями** — файл `<workspace>/.active-project`
   (одна строка = id). Источник истины для скриптов; изменяет его только навык
   `/проект`. В блоке «Проекты» `AGENTS.md` — зеркальная строка `Активный проект: **<id>**`
   (навык держит её синхронной; при расхождении побеждает `.active-project`).
   Файл состояния переживает сессии и перезапуски.
4. **Бюджеты** — `budgetUsdPerDay` per project хранится в реестре (справочно);
   контроль расхода и предупреждения — в дайджестах этапа E6 (soft). **Hard-стоп
   при исчерпании не делаем** — включается отдельным решением после E6.

## Реализация (E5)

- **Реестр** — анкетный ключ `projects: [{id,title,dir,description?,budgetUsdPerDay?}]`
  (`id` — slug `[a-z0-9-]`; `dir` — один сегмент `[A-Za-z0-9._-]` **относительно
  workspace агента**, без `..`; скетч плана `dir: Projects/Dom` интерпретирован так,
  что корень — workspace). В `openclaw.json` не рендерится (meta).
- **Workspace-слой factory** (`plan`/`apply`, идемпотентен, не трогает `openclaw.json`):
  `projects.yaml` (машиночитаемый реестр, managed), `PROJECTS.md` (навигация, managed),
  блок между маркерами `<!-- oc-factory:projects:start/end -->` в `AGENTS.md`
  (managed-блок; остальной файл не трогается, перед правкой — бэкап),
  `skills/проект/SKILL.md` (managed), деревья проектов `<dir>/{PROJECT.md,docs,data,memory,logs}`
  (существующее не перезаписывается; `PROJECT.md` — только создаётся),
  `.active-project` (создаётся при отсутствии = первый проект анкеты).
- **Команды чата `/проект <id>`, `/проект список`, `/проект статус`** — это навык
  (`SKILL.md`, frontmatter `name: проект`); OpenClaw регистрирует slash-команду по
  имени навыка. Кириллица в `name`/имени каталога работает (проверено на сервере).
  Диспетчеризация команды — в модель (default `command-dispatch`), процедура в SKILL.md.
- **`contextInjection`** — в конфиге не трогаем: default `always` = bootstrap-файлы
  (в т.ч. `AGENTS.md` с блоком проектов) впрыскиваются в каждый ход. Поле в схеме —
  переключатель `always|continuation-skip|never`, а НЕ список файлов (список bootstrap
  фиксирован: `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `MEMORY.md`, `BOOTSTRAP.md`;
  произвольные файлы типа `PROJECTS.md` в контекст не впрыскиваются — потому реестр
  дублируется в блок `AGENTS.md`).
- **Пилот — `service`** (3 реальных проекта: `digitalization-uk`, `wifi-public-business`,
  `brand-stopzatop`); `main`/`ksu` не трогаем (правило §10.6).

## Альтернативы (отклонены)

- **Per-чат активный проект** (session-state) — сложнее, для пилота избыточно; вернуться
  при реальной необходимости параллельных контуров.
- **`PROJECTS.md` как отдельный bootstrap-файл** — платформа впрыскивает фиксированный
  набор файлов; `PROJECTS.md` — только навигация «по требованию».
- **Состояние в `projects.yaml`** (поле `active`) — файл managed, навык его не пишет;
  раздельный `.active-project` чище (источник истины vs managed-реестр).
- **Навык-каталог с кириллическим именем** — работает, но выбран ASCII-совместимый
  формат имени `name: проект` + каталог `skills/проект/` (выровнены, как рекомендует
  `creating-skills`).

## Следствия

- Появляется workspace-слой в `plan`/`apply` (секция `workspace[<agent>]`); `export --check`
  (drift) остаётся конфиговым — сверка managed-файлов workspace — тема E7.
- После правки `SKILL.md` нужен `systemctl restart openclaw-gateway`: инвентарь навыков
  кэшируется на время жизни Gateway, а вотчер снапшот в этом окружении не обновляет
  (проверено 2026-10-21; см. `docs/Грабли-и-решения.md` §1.6).
- E6 (T8) надстраивает над реестром: фоновые задачи проектов, дайджесты
  «результаты/проблемы/ресурсы» с usage-разбивкой по проектам, бюджеты.

## Решения E6/T8 (дополнение 2026-10-21)

- **Дайджест — детерминированный скрипт, доставка command job'ом.** Сбор данных
  (`oc-project-digest.py`: проекты/журналы/задачи/usage) выполняет скрипт; доставку
  делает automation **command job** OpenClaw (`--command … --announce --channel … --to …`),
  без агентского хода — 0 токенов, воспроизводимый формат. Агентский ход (turn с
  пересказом) отклонён: дорого и недетерминированно.
- **Привязка задач к проекту — тег `proj-<id>` в имени задачи/automation** (и label/runId);
  `openclaw tasks list` не имеет поля project, тег в имени — самый надёжный маркер для
  дайджеста. Фоновая задача = `openclaw automations` (durable, переживает сессии/рестарты).
- **Журналы проекта — `<dir>/logs/*.md` с маркерами `RESULT:`/`PROBLEM:`** (каждая запись —
  отдельной строкой); дайджест их агрегирует. Формат задан навыком `фон`.
- **Бюджеты — soft-предупреждение в дайджесте** (hard-стоп не делаем, как и решено в E5):
  `budgetUsdPerDay` per проект в `projects.yaml`; сверка — расход агента за день
  (`usage-cost`) против суммы бюджетов; полная per-project разбивка расхода невозможна
  (usage известен только per-agent) — теги задач дают грубую атрибуцию.
- **Конфигурация дайджеста — поле `reports.digest` анкеты** (в конфиг не рендерится),
  синхронизация automation — `oc-reports.py` (declaration-key `factory:<agent>:digest`;
  привязка к анкете сохраняет правило «правки — только через анкету»).
