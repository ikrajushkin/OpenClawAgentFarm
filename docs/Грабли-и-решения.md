## §1.1 — Ubuntu снова включает парольный SSH через cloud-init

- **Отпечаток (2026-09, oc-node1):** после «выключенных» паролей SSH парольная аутентификация внезапно
  работала; `99-*.conf` с `PasswordAuthentication no` не действовал.
- **Первопричина:** Ubuntu кладёт `/etc/ssh/sshd_config.d/50-cloud-init.conf` с `PasswordAuthentication yes`.
  sshd при `Include` берёт **первое** совпадение параметра, поэтому файлы с бо́льшим префиксом (`99-*`)
  игнорируются.
- **Ремедиация:** харденинг положен в файл с префиксом **меньше** — `01-hardening.conf`; порядок файлов
  проверять после каждого апдейта cloud-init.
- **Вывод:** в sshd_config.d выигрывает не «самый новый», а «первый по алфавиту»; всегда проверять
  `sshd -T | grep -i password` фактом, а не именем файла.

## §1.2 — запуск `openclaw` под root даёт token_mismatch

- **Отпечаток (2026-09, oc-node1):** `openclaw …` от root падает с `token_mismatch`.
- **Первопричина:** под root конфигурация ищется в `/root/.openclaw`, тогда как рабочий конфиг и токены —
  у сервисного пользователя `openclaw` (`/srv/openclaw/.openclaw`); оба «инстанса» несовместимы.
- **Ремедиация:** сервисные команды — только через обёртку `oc` (запускает `openclaw` от `openclaw`),
  либо `sudo -u openclaw`; под root напрямую `openclaw`/`oc` не вызывать (зафиксировано в
  [`../CLAUDE.md`](../CLAUDE.md)).
- **Вывод:** CLI-инструменты с per-user состоянием вызывать от владельца состояния; иначе получаешь
  «второй инстанс» с другим токеном.

## §1.3 — правка openclaw.json через `jq --args` обнулила боевой конфиг

- **Отпечаток (2026-10-14, oc-node1):** после «безопасной» правки `openclaw.json` (allowlist плагинов)
  Gateway входит в crash-loop: `Gateway start blocked: existing config is missing gateway.mode`,
  exit `78/CONFIG`; `openclaw.json` — пустой файл (0 байт).
- **Первопричина:** `jq --args 'программа' файл …` трактует **все** оставшиеся аргументы как позиционные
  строки (`$ARGS.positional`), а не как входные файлы; программа получила пустой stdin и выдала пустой
  документ, `mv` заменил им боевой конфиг. Первая же попытка (inline-команда через plink) плыла на
  экранировании PowerShell (`$`, `{}`, кавычки) — её результат был невинным, но создал ложную
  уверенность.
- **Ремедиация:** мгновенно восстановлен из бэкапа `openclaw.json.bak-20261014-security` (сделан перед
  правкой — Gateway поднялся). Новые правила: (1) `cp -a` бэкап **перед любой** правкой конфига;
  (2) вход конфига только явным `< openclaw.json`; (3) `jq empty` валидация результата перед `mv`;
  (4) сложные bash-скрипты передавать файлом (`cmd /c 'plink … bash < file'`), не inline; (5) после
  правки от root — `chown openclaw:openclaw && chmod 600` (иначе всплывает CRITICAL
  `fs.config.perms_world_readable`, и мирно читающийся root-owned 644 конфиг — это дыра).
- **Вывод:** трансформация «в одну команду» опаснее ручной правки: `jq --args` не читает файлы, а пустой
  выход молча становится пустым конфигом. Работа с конфигом = бэкап + валидация + атомарная замена + права.

## §1.4 — CRLF из Windows при заливке файлов на сервер

- **Отпечаток (2026-10-14, oc-node1):** после заливки скриптов и zabbix-конфига
  (`cmd /c 'plink … cat > /путь < файл'`) bash жалуется `set: -\r: invalid option`, появляются файлы
  с `\r` в именах (`zabbix_agentd.conf\r`, `/var/lib/openclaw-metrics\r`), zabbix-ключи
  `custom.…\r` → `Invalid item key format`.
- **Первопричина:** редактор на Windows сохраняет файлы с CRLF; сырые байты уходят на Linux как есть,
  а bash/cron/zabbix-agent воспринимают `\r` как часть токена/имени файла.
- **Ремедиация:** нормализовать LF **локально перед заливкой**
  (`[IO.File]::WriteAllText(path, text.Replace("`r`n","`n"))`); при подозрениях — `sed -i 's/\r$//'`
  на сервере; артефакты с CR-именами искать и удалять (`find … -name '…*' ! -name 'нормальное' -delete`).
- **Вывод:** Windows→Linux транспорт файлов — всегда контроль окончаний строк; `.gitattributes`
  (`infra/** text eol=lf`) покрывает git, но не ad-hoc заливки по SSH.

## §1.5 — PowerShell 5.1 читает `.ps1` без BOM как ANSI

- **Отпечаток (2026-10-14, Windows):** скрипт маскирования секретов с кириллицей в regex-шаблонах
  падает при запуске: `Missing ')' in method call`, `Unexpected token` — при том что файл корректный UTF-8.
- **Первопричина:** PowerShell 5.1 читает `.ps1` **без BOM** в ANSI-кодировке; байты UTF-8 кириллицы
  превращаются в «умные кавычки» и им подобные символы, которые парсер PS считает кавычками/токенами —
  разбор строк ломается (сам файл при этом выглядит нормально).
- **Ремедиация:** либо сохранять `.ps1` с UTF-8 BOM
  (`[IO.File]::WriteAllText(path, text, New-Object Text.UTF8Encoding($true))`), либо держать скрипт
  ASCII-only — кириллицу в regex давать `\uXXXX`-эскейпами (так сделано в
  [`../scripts/mask-secrets.ps1`](../scripts/mask-secrets.ps1)).
- **Вывод:** переиспользуемые `.ps1` в репо — ASCII-only или с BOM; см. также §1.4 (CRLF) —
  обе ловушки транспорта Windows→Linux/Windows.

## §1.6 — инвентарь навыков кэшируется Gateway; вотчер снапшот не поднимает

- **Отпечаток (2026-10-21, oc-node1, E5):** новый workspace-навык (`skills/<id>/SKILL.md`)
  не появляется в `openclaw skills list/check` — и вообще НИКАКОЕ изменение `SKILL.md`
  не видно (маркер в существующем навыке тоже невиден даже с паузой 5 с); все тестовые
  навыки появились только после `systemctl restart openclaw-gateway`.
- **Первопричина:** OpenClaw снапшотит навыки на старте сессии и держит инвентарь на время
  жизни Gateway. Документированный механизм mid-session-обновления («skills watcher»,
  `skills.load.watch`, debounce 250 мс) в этом окружении не срабатывает — вероятно, вотчер
  не следит за `/srv/shared/...` или инвентарь всё равно кэшируется процессом Gateway.
- **Ремедиация:** после добавления/правки/удаления `SKILL.md` — `systemctl restart
  openclaw-gateway` (секунды; активные сессии не теряются, снапшот подхватится на новом ходе),
  затем проверка `openclaw skills list --agent <id> --json` (или `skills check`).
- **Вывод:** навыки = конфигурация, требующая рестарта Gateway (как правка `openclaw.json`);
  в автоматизации (factory apply навыка `/проект`) рестарт — отдельный явный шаг оператора.
  Факты по механике навыков (slash-команды = имя навыка, кириллица в `name` работает) —
  ADR-006.

## §1.7 — batch-гонка deploy/apply; editor append режет хвост файла (E6)

- **Отпечаток (2026-10-21, E6):** `oc-factory apply`, запущенный в одном пакете команд
  параллельно с `oc-factory-deploy.ps1`, отработал по СТАРОЙ анкете («0 изменений», бюджеты
  проектов не применились) — деплой ещё копировал анкеты. Повторный `plan`/`apply` ПОСЛЕ
  деплоя показал и применил дельту корректно.
- **Второй отпечаток (та же сессия):** вставка editor'а по `insert_line` в конец python-файла
  срезала его последнюю строку (её «остаток» всплывал в конце файла) и однажды «съела» тело
  функции (грабля §1.6 в новом виде). Проявляется только `py_compile`/тестом.
- **Ремедиация:** деплой и apply — строго последовательными командами (не гонять одним
  batch); правки кода — только якорь-замены маленьких кусков + обязательный
  `python -m py_compile` (и локальный тест) после КАЖДОЙ вставки; длинные новые файлы
  писать несколькими вставками с проверкой после каждой.

## §1.8 — install плагинов: EACCES от cwd сессии, capability consent (N4)

- **Отпечаток (2026-10-23, N4):** `openclaw plugins install @openclaw/tokenjuice` падает
  «Command failed during launch or output capture (EACCES)» — при этом `--version`/`plugins list`
  работают. Стек: `resolveNpmSpecMetadata` → spawn дочерней команды (npm) с **cwd текущей
  сессии**; запуск из-под root даёт cwd `/root` (drwx------), куда у сервисного пользователя
  `openclaw` нет доступа → EACCES на launch.
- **Ремедиация:** запускать openclaw-команды из нейтрального каталога:
  `cd /srv/openclaw && sudo -u openclaw env HOME=/srv/openclaw openclaw plugins install <spec>`.
  Второй барьер установки — capability consent: плагин требует `--accept-capabilities` (без флага —
  «requires capability consent»). Совместимость версий инсталлятор проверяет сам: 2026.10.6
  несовместим с runtime 2026.8.2 → выбрана ближайшая совместимая `@openclaw/tokenjuice@2026.8.2`.
  После install — `systemctl restart openclaw-gateway` (без рестарта плагин не грузится).
- **Процессное:** при отказе plink в аутентификации (ключ Pageant не найден) — не искать ключи
  по дискам, а сразу спросить заказчика запустить Pageant (кей `rsa-key-20240224`).
- **Вывод:** установка плагинов = управляемая операция: consent + allowlist (`plugins.allow`
  обновляется install'ом автоматически) + рестарт; проверка — `openclaw plugins info <id>`
  (Status: loaded) и smoke-тест агентом (noisy exec → компактный результат).
