## 1. Текущее состояние (факты, что уже есть в платформе)

### 1.1. Как настраиваются агенты сейчас

Три агента (`main`, `service`, `ksu`) — каждый вручную: секция `agents.entries.<id>` в
`/srv/openclaw/.openclaw/openclaw.json` + `bindings[]` + аккаунты каналов + token-файлы.
Поля агента по факту: `identity, workspace, agentDir, model(primary+fallbacks), models(params),
subagents(allowAgents, model), tools(profile/alsoAllow), thinkingDefault`.

### 1.2. Резерв платформы (в схеме OpenClaw 2026.8.2, пока НЕ используется)

Сверено `oc config schema`:

- **`modelPolicy.allow`** — per-agent allowlist моделей: алиасы, `provider/model`, wildcard
  `provider/*` / `provider/namespace/*`; пусто = любой модели можно. Это готовый механизм T2;
- **`subagents`** — полный набор: `allowAgents, delegationMode(suggest|prefer), maxSpawnDepth,
  maxConcurrent, maxChildrenPerAgent, requireAgentId, runTimeoutSeconds, model, thinking,
  announceTimeoutMs, archiveAfterMinutes` — готовый механизм T3;
- **`tools`** — `profile(minimal|coding|messaging|full)`, `allow`, `alsoAllow` — профили полномочий;
- **`skills`, `sandbox`, `utilityModel`, `contextInjection`, `memory`, `heartbeat`** (per-agent),
  `runtime`, `groupChat`, `tts` — расширения агента;
- **CLI:** `oc agents add --non-interactive --json`, `oc agents bind/unbind`, `oc agents set-identity`,
  `oc config patch --file|--stdin [--dry-run]` (JSON5, валидация по схеме, «одна проверяемая запись»),
  `oc config schema/validate`, `oc agents delete` (**destructive** — prune workspace/state),
  `oc tasks` (durable background tasks + TaskFlow), `oc cron` (автоматизации с delivery→канал).

### 1.3. Каналы (схема vs факт)

| Канал | В схеме/плагинах | Сейчас | Секрет |
|---|---|---|---|
| Telegram | есть (мультиаккаунт) | 3 аккаунта (main/ksu/service) | `/srv/openclaw/secrets/telegram-*.token` |
| MAX | есть | 1 аккаунт (→ service) | `max-default.token` |
| Nextcloud Talk | **плагин `nextcloud-talk` есть** | не подключён | TBD |
| Почта (входящие) | **плагин `imap`** (disabled): IMAP → TaskFlow | не подключён | imap-учётка |
| Внешние события | **плагин `webhooks`** (disabled) → TaskFlow | не подключён | подписи |
| Discord/Slack/WhatsApp/MSTeams/… | есть в схеме | не подключены | по demand |

### 1.4. Ценное состояние, которое надо перенести (чек-лист T6)

1. `openclaw.json` (идентичности, роутинг, параметры моделей) — десятки `.bak-*` как история;
2. `agents/<id>/agent/*`: IDENTITY.md, SOUL.md, USER.md, MEMORY.md, AGENTS.md, DREAMS.md, `skills/`;
3. workspace-контент: `/srv/shared/Workspace`, `/srv/shared/Projects/{Service,Ksu}`;
4. секреты: `secrets/*.token` (токены каналов) + auth-store (ключи polza\* — **в конфиге их нет**);
5. `bindings[]` и allowFrom-списки (кому можно писать);
6. cron-автоматизации (10 шт., включая рабочий контур BAS-IP «такт»/«уточняющий»);
7. накопленные данные бэкапов `/srv/openclaw/backups` (уже под автоматизацией, OPF-4).

## 2. Целевая архитектура: «Фабрика агентов»

**Принцип: анкета (декларативный профиль) — источник истины; `openclaw.json` — производный артефакт.**
Правка агента = правка анкеты → `plan` (diff) → `apply`. Никаких ручных `jq` по живому конфигу (грабли §1.3).

```
agents/<id>.yaml ──render──► patch.json5 ──oc config patch --dry-run──► ok ──► apply
       │                                                        │
       ├── scaffold workspace (IDENTITY/AGENTS/MEMORY-шаблоны, дерево каталогов)
       ├── secrets refs (tokenFile: пути, НЕ значения)
       └── cron-объявления (heartbeat, дайджесты проектов)
```

### 2.1. Компоненты

1. **Анкета** `agents/<id>.yaml` — формат §3. Каталог `agents/` в этом репо (git = источник истины,
   секреты — только ссылки).
2. **`scripts/oc-agent-factory.py`** (stdlib, стилистика `gen-knowledge-graph.py`) — команды:
   - `new` — интерактивный опросник (или `--from template`) → YAML анкеты;
   - `export` — reverse: живой конфиг → YAML (миграция + контроль дрейфа);
   - `validate` — схема анкеты + сверка ссылок (стеки, роли, пресеты, секреты-файлы);
   - `plan` — diff «живой конфиг vs анкета» (человекочитаемый);
   - `apply` — render → `oc config patch --dry-run` → (ok) → apply + scaffold + cron; **бэкап
     `openclaw.json` перед записью**; merge-семантика patch: массивы заменяются целиком →
     списковые пути через `--replace-path`;
   - `destroy` — только `--confirm`, с бэкапом и `export`-снимком (агент + его роутинг).
3. **Библиотеки профилей** (анкета ссылается по имени, не копирует):
   - `_stacks.yaml` — стеки моделей: `ds-economy` (deepseek-v4.1-flash + фолбэки), `ds-pro`
     (v4-pro-0813), `local-only` (Ollama/локальные), `mixed` (внешние + локальные utility);
   - `_toolsets.yaml` — наборы инструментов: `messaging`, `coding`, `research`, `ops`;
   - `_roles.yaml` — роли субагентов: `researcher` (дешёвая модель, разведка), `coder`,
     `doc-writer`, `ops-runner` (свои таймауты/глубина/модель);
   - `_channels.yaml` — пресеты каналов: `telegram-bot`, `max-bot`, `nc-talk`, `mail-imap`, `webhook-in`.
4. **Секреты**: анкеты содержат только ссылки (`tokenFile: /srv/openclaw/secrets/…`); чек-лист
   выпуска токенов (BotFather, MAX, IMAP-учётка) — в пресете канала. Значения — никогда в git.
5. **Контроль дрейфа**: cron/pre-commit `factory export --check` → расхождение «конфиг ≠ анкеты»
   фиксируется (СОСТОЯНИЕ/Грабли); это же ловит ручные правки мимо фабрики.

### 2.2. Почему не «просто `oc agents add`»

`agents add` покрывает workspace+model+bind. Политики моделей, субагенты, tools, пресеты каналов,
автоматизации/дайджесты — всё ещё руками в `openclaw.json` (риск §1.3, неповторимость). Фабрика
объединяет шаги в один воспроизводимый конвейер с dry-run и откатом; штатный `config patch`
используется как исполнитель — не изобретаем свой writer конфига.

## 3. Анкета: формат (скетч)

```yaml
# agents/ksu.yaml — анкета агента
id: ksu
identity: { name: "Помощник", emoji: "🧑‍🏫", theme: "…" }
workspace: /srv/shared/Projects/Ksu
projects:                       # OPF-9: реестр проектов агента (см. §7)
  - { id: dom,  title: "Домашние дела", dir: Projects/Dom }
  - { id: ksu,  title: "Проект КСУ",   dir: Projects/Ksu }

models:
  stack: ds-economy             # из _stacks.yaml
  policy:
    allow: ["polza-ksu-ds/*", "ollama/*"]   # T2: жёсткий allowlist (modelPolicy.allow)
  utility: local:ollama/bge-m3  # utilityModel: локальная, не тратит внешний бюджет
  thinking: max

subagents:                      # T3
  allowAgents: [ksu]
  roles: [researcher, doc-writer]   # из _roles.yaml → allowAgents пополняется ролями
  delegationMode: prefer
  maxSpawnDepth: 2
  maxConcurrent: 2
  runTimeoutSeconds: 900

tools:
  toolset: messaging            # из _toolsets.yaml → tools.profile + allow
  alsoAllow: [browser, message, web_search, web_fetch]

channels:                       # T4
  - preset: telegram-bot
    account: ksu
    allowFrom: ["1308310289"]
    secretRef: /srv/openclaw/secrets/telegram-ksu.token

automations:
  - { name: "Heartbeat (ksu)", schedule: "every 1d", delivery: none }
reports:                        # T8 (OPF-9): периодические доклады
  - { schedule: "cron 0 21 * * * @ Europe/Moscow", to: telegram:1308310289,
      include: [results, problems, usage] }

limits:
  budgetUsdPerDay: 10
```

**Семантика рендера:** `models.stack` → `model.primary/fallbacks` + `models{}` + `modelPolicy.allow`;
`roles` → allowAgents (+ опционально отдельные role-агенты со своим стеком); `toolset` → `tools.*`;
`channels` → `channels.<type>.accounts.<id>` + `bindings[]` + `tokenFile`; `automations/reports`
→ cron-задачи через `oc cron`; `projects` → `projects.yaml` + дерево каталогов + команды чата.

## 4. Перенос текущих ценных данных (T6, без потерь)

| Шаг | Действие | Защита |
|---|---|---|
| M1 | Полный снимок: `openclaw.json`, `agents/`, `secrets/` (список имён), auth-store, cron-выгрузка | `oc-backup.sh` (OPF-4) + отдельный tar-снимок + git-копия non-secret |
| M2 | `factory export` → `agents/{main,service,ksu}.yaml` | reverse-инжиниринг, значения секретов не выгружаются |
| M3 | Сверка: `factory plan` для каждого агента = **пустой diff** | критерий эквивалентности, иначе анкета неполна |
| M4 | Анкеты закоммичены (секреты — только ссылки, маскирование `mask-secrets.ps1`) | git = источник истины |
| M5 | Все дальнейшие правки — только через `edit/plan/apply` | запрет ручных правок живого конфига (кроме break-fix, с последующим export) |
| M6 | Ролбек-план: `openclaw.json.bak-*` + бэкапы §M1 + `export`-снимок перед каждым apply | откат = восстановление файла + `systemctl restart openclaw-gateway` |

Отдельно: перенос cron-задач (BAS-IP-контур — рабочий, не трогать в M), allowFrom-списков,
привязок полномочий (`tools.elevated` — сейчас глобально enabled, кандидат на per-agent ужесточение).

## 6. Субагенты и «специфические задачи» (T3)

- **Роли** = именованные профили в `_roles.yaml`: собственный стек моделей (напр. researcher —
  дешёвая flash-модель), `runTimeoutSeconds`, `maxSpawnDepth`, `requireAgentId`;
- Анкета декларирует `roles: [...]` — factory раскладывает в `subagents.allowAgents` и, при
  необходимости, в отдельные role-агенты (не-канальные, без bindings);
- `delegationMode: prefer|suggest` — жёсткость делегирования per-agent;
- `sandbox` (Docker-изоляция исполнения кода) — отдельное решение (сейчас 0 рантаймов,
  Оркестрация-агентов §4.7), в фабрике — поле `tools.sandbox: none|docker`, дефолт `none`;
- A2A (агент→агент) сейчас disabled — при включении попадает в `plugins.allow` и в анкету как
  меж-агентные вызовы `subagents.allowAgents`.

## 7. Этап 2: мультипроектность (T7/T8, OPF-9) — концепция

**Модель.** Проект = изолированная область данных агента:

```
/srv/shared/Projects/<Agent>/<Project>/
├── PROJECT.md      # карточка: цель, статус, ссылки
├── docs/           # документы проекта
├── data/           # рабочие данные
├── memory/         # память проекта (свой индекс)
└── logs/           # журналы фоновой работы
```

- **Реестр проектов** — `projects` в анкете (§3) + `PROJECTS.md` в workspace (навигация агента);
- **Переключение командами чата**: custom-команды `/проект <id>`, `/проект список`,
  `/проект статус` (реализация — `commands`/skills OpenClaw); активный проект хранится в состоянии
  агента и подставляется в контекст через `contextInjection` (поле уже есть в схеме);
- **Фоновая работа**: `oc tasks` (durable background tasks / TaskFlow) с привязкой к проекту +
  cron-автоматизации проекта; задачи переживают перезапуск сессии;
- **Периодические доклады** (T8): cron-дайджест по проекту в канал владельца —
  **результаты / проблемы / ресурсы**; ресурсы — из `oc gateway usage-cost --json` (учёт уже
  работает, OPF-6) с разбивкой по агенту/проекту (теги задач + `limits.budgetUsdPerDay`);
- **Изоляция**: права shared-зоны (ADR-003, UMask 0002/setgid), отдельные memory-индексы проекта;
  кросс-проектный обмен — только явный (через `/srv/shared/Inbox` или команду).

**Открытые вопросы для ADR-006** (проработать на этапе E5):
1. семантика переключения: активный проект — per-чат или per-агент глобально;
2. что попадает в контекст при переключении (гидратация из PROJECT.md/memory);
3. хранение «текущего проекта» между сессиями (state агента vs сессионная команда);
4. бюджеты/лимиты: hard-стоп при исчерпании vs предупреждение в дайджест.

## 9. Риски и ловушки

| Риск | Митигация |
|---|---|
| Грабли §1.3: ручная правка `openclaw.json` обнуляет конфиг | только `oc config patch --dry-run` → apply; бэкап перед каждой записью |
| Merge-семантика patch: массивы заменяются целиком | `--replace-path` для списков; покрыть тестами factory |
| Секреты (токены, ключи polza\*) утекут в git | анкеты = только ссылки; `mask-secrets.ps1` при выгрузках; контроль форматов |
| `agents delete` уничтожает workspace/state | `destroy` только `--confirm` + export-снимок + бэкап |
| Ключи моделей живут в auth-store, не в конфиге | процедура переноса/выпуска — отдельный чек-лист E1 |
| Новые плагины каналов не в `plugins.allow` | пресет канала = +id в allowlist (валидация в `validate`) |
| Ручные hot-fix мимо фабрики → дрейф | drift-контроль `export --check` (cron) |
| CRLF/кодировки при заливке скриптов (§1.4/§1.5) | LF-нормализация, `.ps1` ASCII-only/BOM, сверка md5 |

## 10. Решения (согласовано 2026-10-14)

1. **Анкеты живут в этом репо `agents/`** — git-история, рядом с docs. ✅
2. **Формат анкеты — YAML** (реализовано: PyYAML 6.0.3 есть и локально, и на oc-node1). ✅
3. **Права моделей — жёсткий `modelPolicy.allow`**, но при создании НОВОГО агента сначала
   берётся стек по умолчанию (`stack:` из `_stacks.yaml`, allowlist = модели стека), далее
   владелец правит allowlist в своей анкете. ✅
4. **Пилот мультипроектности — на `service`** (изолированный контур). ✅
5. **Локальные модели — сначала тщательная разведка**, ничего не ломать в текущих механизмах
   (см. §11). Стек `local-only` заморожен до отдельного решения. ✅
6. **Общий принцип миграции — минимальные изменения и неудобства для текущих пользователей**:
   `export` → анкеты с diff=0; apply только после plan; пилоты (new/apply/destroy,
   мультипроектность) — только на `service`; `main`/`ksu` не трогать без необходимости.
