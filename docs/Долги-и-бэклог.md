## OPF-5 — находки `oc security audit` не закрыты (1 critical, 2 warn)

- **Статус:** ✅ закрыт 2026-10-14 (обнаружено 2026-10-14, см. [Оркестрация-агентов.md](Оркестрация-агентов.md))
- **Что:** (1) CRITICAL — `plugins.allow` не задан, глобальные extensions (`duckduckgo`, `max`) грузятся
  без allowlist; (2) WARN — нет `gateway.auth.rateLimit` при bind не loopback (172.18.0.1); (3) WARN —
  плагин `signal` без integrity-метаданных. Плюс: `tools.elevated` включён без политики approvals.
- **Что сделать:** задать `plugins.allow`; `gateway.auth.rateLimit` (напр. 10 попыток/60с, lockout 300с);
  переустановить или удалить signal-плагин; настроить approvals-allowlist для exec.
- **Критерий:** `oc security audit` — 0 critical / 0 warn.
- **Решение (2026-10-14):** задан `plugins.allow` — 20 доверенных id (signal и неиспользуемые
  provider/инструментальные плагины исключены); `gateway.auth.rateLimit = {maxAttempts:10, windowMs:60000,
  lockoutMs:300000}`; плагин `@openclaw/signal` **удалён** (`oc plugins uninstall signal --force` —
  вместе с install-записью, это закрыло и WARN про integrity); конфиг приведён к `openclaw:openclaw 600`
  (попутно закрыт CRITICAL `fs.config.perms_world_readable`, появившийся после правки — см. §1.3).
  Факт: `oc security audit` → **0 critical · 0 warn · 2 info** (info: сводка поверхности атаки,
  «DM MAX заперты» — это политика pairing, не находка). Вне критерия осталась политика approvals для
  `tools.elevated` — перенесена в план развития ([Оркестрация-агентов.md](Оркестрация-агентов.md) §4.6).

## OPF-7 — консистентность и живость агентского контура

- **Статус:** ✅ закрыт 2026-10-14 (обнаружено 2026-10-14)
- **Что:** (1) `heartbeat:main` падает (`agent-runner-failure`) — контроль живности агентов сломан;
  (2) канал Signal включён, но not configured/stopped — мёртвый шум в статусах; (3) workspace агента
  `ksu` — `~/workspaces/Ksu`, вне `/srv/shared` (вопреки ADR-003, вне общей зоны бэкапов);
  (4) идентичности из разных источников (config vs IDENTITY.md); (5) схема ключей polza vs polza-ksu
  (разделение расходов?) не зафиксирована в ADR.
- **Что сделать:** `oc doctor` + `oc cron runs` по heartbeat:main; выключить/поправить Signal; перенести
  workspace ksu в `/srv/shared/Projects/Ksu`; дописать в ADR-004 схему ключей.
- **Решение (2026-10-14):** (1) heartbeat:main — сбой был **разовым** (14.10 06:07, `agent-runner-failure`
  в момент смены токенов/моделей); ручной прогон `oc cron run 6d5c36dd… --wait` → `succeeded`
  («heartbeat completed»), расписание daily работает; (2) Signal закрыт: плагин удалён (OPF-5),
  в `channels list` канала нет, строка в `channels status` — лишь заглушка каталога; (3) workspace
  `ksu` перенесён `/srv/openclaw/workspaces/Ksu` → **`/srv/shared/Projects/Ksu`** (16M, права зоны
  `shared` 2775; config `agents.entries.ksu.workspace` обновлён; проверка — heartbeat ksu
  `succeeded`; старый каталог удалён) — теперь в зоне бэкапов, ADR-003 соблюдён; (4) идентичности
  унифицированы: источник истины — config, IDENTITY.md синхронизированы (main/ksu заполнены из
  config, у service сохранена персонализация); (5) схема ключей polza-ds (main+service) vs
  polza-ksu-ds (ksu, отдельный кошелёк) зафиксирована в
  [ADR-004](ADR/ADR-004-model-chain-deepseek-polza.md) (дополнение).
